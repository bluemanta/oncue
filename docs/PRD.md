# OnCue单词 PRD

Sep 26, 2026 · @ChrisWang

## 概述

一句话定义：遇到一个英文单词时，丢进来就能一次走完"看懂 → 会读 → 读对 → 记住"的极简工具。

| 项目 | 内容 |
| --- | --- |
| 产品名称 | OnCue单词 |
| 版本 | V0.1（第一版，自用验证） |
| 形态 | 手机网页，可"添加到主屏幕"像 App 一样打开 |
| 原型来源 | 在 Grok bot 里跑通的"读词"用法，本工具要做到不依赖 Grok、可独立运行 |
| 核心原则 | 界面只保留两个动作：丢进来、读给它听 |

## 背景与问题

工作中常遇到不认识或读不准的英文单词。现有工具只能各解决一段，没有一个能在遇到的那一刻把四件事一次办完。

用户的四个原始需求：

1. 知道它什么意思
2. 知道它怎么读
3. 最好有一个例句
4. 知道自己读得对不对

| 现有方案 | 能做到 | 缺口 |
| --- | --- | --- |
| 词典类（有道、欧路） | 释义准确，有标准读音 | 不结合原句讲"在这里是什么意思"；不判断你读得对不对 |
| 口语类（ELSA、流利说） | 能练发音、打分 | 要进它的课程体系，不能"随手遇到随手问" |
| 通用 AI bot（如 Grok） | 能结合语境讲解，体验接近理想 | 依赖第三方平台；发音判断靠通用模型"听"，逐音纠错不够稳定 |

产品价值不在"查词"本身，而在把四步闭环压缩到一次操作里，并且第 4 步（读对）要做得靠谱。

## 目标与非目标

本阶段按"自用工具"来做：先证明自己离不开它，再决定是否产品化。

**目标**

- 一次输入，拿到释义、读音、例句三样东西，全程不超过 10 秒
- 跟读后能指出具体哪个音或哪个重音读偏了，并给出改法
- 自动记住查过的词和读错过的音
- 两周内做出可用版本，功能范围不随开发过程扩张

**非目标（本阶段明确不做）**

- 课程、词书、学习计划
- 打卡、排行榜、社交、游戏化
- 账号体系、付费、多用户管理
- 追求细微口音差别的判断（这部分比不上真人老师）

## 目标用户与使用场景

第一用户是自己：英文读写尚可、听说偏弱、每天会接触英文工作材料的职场人。产品化后的目标用户也是这一类人。

| 场景 | 遇到词的方式 | 期望的输入 |
| --- | --- | --- |
| 读英文 RFP、方案、邮件 | 电脑上看文档 | 复制整句粘贴 |
| 刷手机看文章、资讯 | 手机上看到 | 用手机自带文字识别复制后粘贴 |
| 开会、听分享 | 听到一个词，不确定怎么拼 | 打字输入大概拼写 |
| 准备要说出口的内容 | 想确认自己读得对不对 | 按住录音跟读 |

## 核心体验与用户流程

首页只有一个输入框和一个麦克风按钮，所有结果集中在一张卡片上，从上往下看，不需要来回对话。

主流程：

1. **丢进来**：打字或粘贴整句，首页有一键粘贴按钮
2. **识别目标词**：如果是整句，自动判断要查哪个词；判断不了就让用户点选
3. **出结果卡片**：释义（含语境义）、音标与重音、易错点、例句、播放按钮
4. **跟读**：按住麦克风读这个词或例句，松开即提交
5. **看反馈**：三档结果——读对了 / 基本对（指出 1 处问题）/ 不对（给慢读示范，引导再跟一遍）
6. **自动记录**：查词记录和读错的音存下来，下次再查同一个词时提醒

体验原则：

- 每次反馈只指出**最主要的一个问题**，不一次挑出所有错
- 用可反复点击的播放按钮代替"发一条语音"，想听几遍听几遍
- 失败要说清楚：比如录音太短、环境太吵，直接告诉用户原因，不给一个不可靠的分数

## 功能需求

第一版（P0）只做闭环必需的 4 项；P1 在自用验证通过后再加。P0 = 没有它就不成立，P1 = 有了更好。

| 编号 | 功能 | 优先级 | 验收标准 |
| --- | --- | --- | --- |
| F1 | 文字输入：打字或粘贴 | P0 | 首页有一键粘贴按钮；输入整句时能自动找出目标词，找不准时可手动点选；输入中混有中文说明时按"输入处理规则"拆解，卡片显示、朗读和评测只用其中的英文原句 |
| F2 | 截图输入 | P1 | 第一版不做。截图可先用手机自带的文字识别复制出英文，再粘贴输入 |
| F3 | 结果卡片 | P0 | 内容符合"结果卡片内容规范"，从提交到出结果不超过 10 秒 |
| F4 | 标准读音播放 | P0 | 单词可慢速、常速播放，例句可播放，默认美音，可切换英音 |
| F5 | 跟读评测 | P0 | 能指出具体读偏的音或重音，结果分三档；录音无效时明确提示原因 |
| F6 | 查词记录 | P1 | 再次查同一个词时提示"你某天查过" |
| F7 | 错音本 | P1 | 自动收集读错过的音，按出错次数排序 |
| F8 | 间隔复习 | P1 | 按"快忘的时候再提醒一次"的节奏推送复习，例如第 1、3、7 天 |
| F9 | 电脑浏览器划词查询 | P1 | 在网页上选中单词即可调出结果卡片 |
| F10 | 例句背景配置 | P1 | 用户可提前设置自己的行业、岗位等背景，例句按设置生成；未设置时默认职场和销售场景 |

间隔复习（F8）：一种复习方法，不是每天把所有词都过一遍，而是在你快要忘记某个词的时候提醒你复习一次，用更少的次数记得更牢。

## 输入处理规则

**用户输入的原始文字**和**要处理的英文原句**是两样东西，不能当成一个。

用户常常会在英文旁边写一句中文说明，例如"帮我查一下这句话里的 schedule 是什么意思，怎么读？"。系统先从输入里拆出英文原句和目标词；卡片顶部显示的原句、送去语音合成的文本、送去发音评测的参考文本，**都只用拆解后的干净英文**。不拆解会导致中文被当成原句显示、被英文音色朗读、被送进发音评测。

用户的额外说明**只用于定位目标词，不改变结果卡片的结构与字段顺序**。卡片每次都长一样这条原则优先。

| 输入情况 | 处理方式 |
| --- | --- |
| 整句英文 | 自动找出目标词；判断不准时让用户点选 |
| 整句英文 + 中文说明，说明里点了名 | 以用户点名的词为准，优先于自动判断 |
| 只有单词，没有原句 | 正常出卡片，但不显示语境义 |
| 一句里有多个生词 | 第一版只查一个，默认取第一个，并在卡片上说明 |
| 输入里没有任何英文单词 | 明确提示"没找到要查的英文单词"，不猜测、不编造 |

## 结果卡片内容规范

卡片固定按下表顺序从上往下排列，每次输出结构都一样，方便形成阅读习惯。

| 顺序 | 模块 | 内容要求 | 示例（以 pipeline 为例） |
| --- | --- | --- | --- |
| 1 | 语境义 | 仅在输入整句时出现，一句话说明这个词在这句话里的意思 | 在"We have a strong pipeline this quarter"里指"商机储备" |
| 2 | 释义 | 最常用的 2–3 个中文义项，职场义项优先 | 管道；（销售）商机管道；（项目）流程 |
| 3 | 读音 | 默认显示美式音标，可切换英式；标出重音在哪个音节，配慢速、常速播放按钮 | /ˈpaɪp.laɪn/，重音在第一个音节 |
| 4 | 易错点 | 中国人最容易读错的 1–2 处，说明怎么改 | 重音不要放在 line 上 |
| 5 | 例句 | 1–2 句，当前限定职场和销售场景，每句都能播放 | Let's review the pipeline before Friday. |
| 6 | 跟读入口 | 麦克风按钮，可选择读单词或读例句 | — |

以上示例只是说明格式，正式内容由系统实时生成。

## 技术方案（通俗版）

全部服务放在腾讯云，直接用已有的服务器、域名和 ICP 备案，大陆用户可以稳定访问。第一版能省则省，但每一块都留好"变大时怎么升级"的路。

**三条架构原则**

- **统一接口**：大模型、语音、评测都通过一层统一接口调用，像"转换插头"，以后换服务商只换插头，产品其他部分不动
- **先轻后弹**：第一版跑在已有服务器上，零额外成本；用户变多后，后端迁到腾讯云云函数（Serverless：不用自己管服务器，按调用次数收费，人多时自动扩容）
- **标准数据库**：用最通用的 PostgreSQL，以后换托管数据库或换云都能直接搬

| 环节 | 选用 | 这是什么 | 备注 |
| --- | --- | --- | --- |
| 部署 | 已有腾讯云服务器 + 已备案域名 | 放网页和后端程序的地方 | 已完成 ICP 备案 |
| 安全连接 | 腾讯云免费 SSL 证书 | 让网址变成 https 开头的加密连接 | 必需：浏览器只允许 https 网页使用麦克风 |
| 后端 | 服务器上的轻量程序 | 用户看不到的部分，负责保管密钥、调用各项服务 | 用户变多后迁到云函数 |
| 数据库 | PostgreSQL，第一版装在服务器上 | 云端的一张表，记录查词和错音 | 需设置定期备份；变大后换腾讯云托管数据库 |
| 解释意思、写例句 | 腾讯云上的 DeepSeek 接口（备选：腾讯混元） | 按次付费调用 AI | 国内已备案模型 |
| 读给你听 | 腾讯云语音合成（TTS） | 文字转语音 | 默认美式英文音色 |
| 判断读得对不对 | 首选候选：腾讯云口语评测 | 把录音和标准发音逐个音素比对打分 | 第二周实测后定；不达标再测讯飞 |
| 音频存储 | 腾讯云对象存储（COS） | 云端的"网盘"，存生成好的读音文件 | 同一个词只合成一次，之后直接取，更快也更省钱 |

**发音评测的选型要点**

- 判断发音有两种做法。第一种是先把语音转成文字，再看被听成了哪个词：只能说"你把 sheet 读得像 shit"，说不出错在哪个音。第二种是专门的发音评测服务：按音素逐个打分，能指出"th 读成了 s"。本产品**必须用第二种**。
- 音素是最小的发音单位，比如 think 可以拆成 th、i、ng、k 四个音。
- 各家对"重音"的判断支持程度不一，选型时要拿自己常读错的 20 个词实际测一遍再定。

**成本估算**：服务器和域名已有，新增的只是按次计费的服务。自用量级下每次查词加评测大约几分钱，每月通常几十元以内；这是量级估算，以腾讯云实际定价为准。

**产品化时的合规提醒**：面向公众开放时，除已有的 ICP 备案外，调用大模型生成内容的应用可能还需要在属地网信办办理生成式 AI 应用登记，届时再具体确认。

| 形态 | 优点 | 代价 | 阶段 |

| 电脑浏览器插件 | 看英文 RFP、网页时划词即查，最贴合读材料的场景 | 需要单独开发一个插件 | V0.2 |

## 数据与隐私

只存学习需要的最少数据；录音评测完即删，不长期保存。

| 数据 | 是否保存 | 用途 |
| --- | --- | --- |
| 查过的词、时间、来源句 | 保存 | 查词记录、复习提醒 |
| 读错的音及次数 | 保存 | 错音本 |
| 跟读录音 | 不保存，评测完即删除 | 仅用于当次评测 |

注意：粘贴的整句可能包含工作材料（如客户 RFP 内容），会发送给第三方大模型和评测服务处理。第一版自用可以接受；产品化前需要选择明确不拿用户数据训练模型的服务商，并在界面上提示用户。

## 成功指标

第一版只看一条主指标：自己连续 14 天使用，每天至少 3 次。达不到就先改体验，不加新功能。

| 指标 | 目标 | 说明 |
| --- | --- | --- |
| 连续使用 | 14 天，每天 ≥ 3 次 | 主指标，决定是否进入下一阶段 |
| 出结果速度 | ≤ 10 秒 | 从提交到卡片完整显示 |
| 纠错命中 | 自测 20 个常错词中，能准确指出问题的 ≥ 16 个 | 用于发音评测服务选型 |
| 跟读完成率 | 查词后点了跟读的比例 ≥ 50% | 看"读对"这一步是否真的被用起来 |

## 风险与待决问题

最大的风险不是技术，而是范围失控：做着做着想加功能，最后拖到做不完。

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 开发中不断想加新功能 | 两周做不完，热情耗尽 | 只做 P0，新想法一律记进 P1 清单，决策点之后再议 |
| 发音评测不准，尤其是重音 | 第 4 步不可信，产品核心价值打折 | 上线跟读前先做选型实测，不达标就换服务商或调整反馈方式 |
| 整句里找错目标词 | 结果卡片答非所问 | 识别不确定时让用户点选目标词 |
| 大厂同类功能已覆盖 | 产品化后难以获客 | 产品化前先找 10 位同类用户验证差异点是否成立 |
